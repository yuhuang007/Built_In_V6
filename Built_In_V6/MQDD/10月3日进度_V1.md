# 聋哑人智能翻译终端：2026 年 10 月 3 日进度（V1）

> 交接目的：本文把截至 2026-10-03 的需求、决策、硬件事实、已实现代码、实机验收证据与下一步行动集中记录。新的开发者或 AI 应先读本文，再读 `docs/bringup/` 下的分项记录；未经验证不要改动已验通的板级驱动、C6 固件或本地密钥文件。

## 1. 项目要做什么

项目名称为“聋哑人智能翻译终端”。当前目标不是一次性完成量产产品，而是在现有 ESP32-P4X Function EV Board 套装上，逐步构建一个可演示的原型：

1. 从板载麦克风采集语音；
2. 经 Wi-Fi 发送到云端语音/对话服务，取得实时或最终文字；
3. 在 7 英寸触摸屏以大字字幕呈现，后续扩展为面向听障用户的交互界面；
4. 将云端生成的语音通过外接扬声器播放，实现面向聋哑/听障沟通场景的双向辅助；
5. 后续接入广角摄像头，为手语/视觉交互预留能力。

当前采用“先逐条打通硬件和基础链路，再接云端能力”的策略。这样每一步都有可复现证据，出现问题时可以精确定位在显示、音频、网络或云端协议层，而不会把问题混在一起。

## 4. 总体架构与选型

```text
板载麦克风 ─┐
             ├─ ES8311 ADC ─ I2S RX ─┐
外接扬声器 ◄─┴─ ES8311 DAC ◄ I2S TX ─┤
                                           │
7 英寸 MIPI-DSI + GT911 ◄── LVGL UI ◄── ESP32-P4 主应用
                                           │
                              SDIO 4-bit ──┤
                                           ▼
                                     板载 ESP32-C6
                                           │ Wi-Fi
                                           ▼
                          竞赛“硬件对话智能体”云服务
                      （ASR → 对话/翻译 → TTS）

广角 MIPI-CSI 相机 ──────────────────────► 后续视觉/手语模块
```

### 4.1 P4 端软件职责

- 初始化显示、触摸、音频与网络；
- 采集并按云协议分帧上传 16 kHz / 16-bit / 单声道 PCM；
- 显示网络状态、录音状态、ASR 中间/最终字幕、故障提示；
- 将 TTS 返回的 PCM/WAV（以云端协议为准）送入 ES8311 播放；
- 实现连接保活、断线重连、超时、取消会话和本地错误处理。

### 4.2 云端选择与理由

主链路推荐使用命题 PDF 提到的**硬件对话智能体**。它能将 ASR、对话编排和 TTS 放进同一官方 IoT 语音链路，最符合竞赛资源、延迟更可控，也避免首个原型同时整合三套独立厂商 API 的鉴权、音频格式与会话管理风险。

火山边缘大模型网关（AI Gateway）是备选文本能力：可用于后续文字翻译、上下文语义改写、设备控制指令或结构化回答；不应承担低延迟实时音频流的主通道。

### 4.3 为什么不重写“操作系统”

P4 固件采用 ESP-IDF + 官方 BSP/组件，不运行 Linux 式通用操作系统，也没有“原系统占用大量性能”的问题。ESP-IDF 的 FreeRTOS、驱动和网络栈是 P4 裸机/RTOS 正常开发基础。完全自行重写启动、显示、I2S、SDIO、Wi-Fi 协处理器协议会显著提高风险，且不会给这个原型带来可验证收益。应用代码仍可完全自主设计，性能关键缓冲放在 32 MiB PSRAM，实时 I/O 放在合适的 FreeRTOS 任务中。

## 6. 按时间的实施与验收记录

### 阶段 1：P4X 最小工程、构建、烧录、诊断 —— 已完成

做法：建立 `esp32p4` 工程，使用隔离 Python 和构建脚本；烧录至 COM20，在串口输出芯片、Flash、PSRAM、堆内存、复位与 SDK 信息。

实测：P4 rev v3.2、双核 400 MHz；Flash 16 MiB；PSRAM 32 MiB/200 MHz，内存测试通过。当前应用二进制约 1.24 MiB，2 MiB factory 分区仍约有 41% 空间；两个 6 MiB OTA 分区已预留。

详细证据：[01-p4x-baseline.md](../docs/bringup/01-p4x-baseline.md)。

### 阶段 2：原装屏幕和触摸 —— 已完成

做法：采用官方 P4 Function EV Board BSP，而非手写 MIPI-DSI、EK79007 初始化序列或 GT911 引脚配置。启动 LVGL 验证页；点击屏幕后显示触摸坐标并输出串口日志。

实测：用户确认原装屏显示正常、触摸也正常；串口识别 EK79007、1024×600 和 GT911。存在 `GPIO 26 is not usable` 的背光相关警告，但实际画面和背光正常，作为非阻塞待观察项，暂不破坏已通过的 BSP 配置。

详细证据：[02-display-touch.md](../docs/bringup/02-display-touch.md)。

### 阶段 3：板载麦克风和外接扬声器 —— 已完成

做法：使用 BSP 的 ES8311 麦克风/扬声器初始化函数，保持套装既定 I2C/I2S 引脚。触摸后录制 3 秒 PCM（16 kHz、16-bit、单声道），将 96,000 字节暂存 PSRAM，录制完成才回放，以避免实时声学反馈。

实测：ES8311 初始化成功，用户确认“录音和回放都是正常的”；屏幕出现 `PASS: microphone recorded and speaker playback completed`。这张实机屏幕照片也已由用户提供。

详细证据：[03-audio.md](../docs/bringup/03-audio.md)。

### 阶段 4：网络与云端语音链路 —— 网络已完成，云端待授权

做法：P4 端加入 NVS、`esp_netif`、事件循环、`esp_wifi_remote` 与 ESP-Hosted；Wi-Fi 凭据通过仅本地的 `secrets/p4x_wifi.h` 注入，日志刻意不输出 SSID/密码。构建、刷写网络版后读取 COM20 启动日志。

本轮实机日志依次确认：

```text

Identified slave [esp32c6]
Transport active

sta ip: 10.168.29.7, mask: 255.255.255.0, gw: 10.168.29.1
```

结论：P4 ↔ C6 的 SDIO 四线连接、ESP-Hosted、Wi-Fi 关联和 DHCP 均已实机通过。构建、刷写与监视过程中已关闭残留 `idf_monitor` 进程，避免 COM20 被多进程占用；本轮结束后也已释放串口。

详细证据：[04-network-cloud-voice.md](../docs/bringup/04-network-cloud-voice.md)。

## 8. 下一步行动清单（严格顺序）

### 8.1 用户需要准备的云端材料

在竞赛资源页面开通“硬件对话智能体”，创建或绑定目标设备后，提供以下**非敏感文档信息**给开发者；真实密钥请写入 `secrets/` 本地文件，不要发送到聊天或提交 Git：

1. 官方接入文档、控制台页面链接或清晰截图；
2. 服务名称/智能体名称、设备 ID 或 Client ID；
3. 服务地址和协议（HTTPS、WebSocket、MQTT 或厂商 SDK）；
4. 认证字段说明（Token/API Key/Secret 的字段名、刷新规则和有效期）；
5. 是否支持实时流式 ASR；音频上行格式、采样率、分帧大小、编码与结束标记；
6. ASR 中间结果/最终结果的 JSON 示例；
7. TTS 返回格式、采样率、位宽、声道、编码及是否流式；
8. 并发、时长、流量或比赛账号的调用限制。

建议创建一个 Git 忽略的 `secrets/cloud_voice.h` 或等价配置文件，仅由代码包含；仓库中只保留没有真实值的 `.template` 示例。

### 8.2 云端资料到位后由开发实施

1. 定义云端会话状态机：空闲 → 录音/上行 → 等待/展示中间 ASR → 最终文本 → TTS 下行播放 → 空闲/错误；
2. 保持当前已验证的 16 kHz/16-bit/mono PCM；按官方要求切为 20 ms 或指定大小的分帧，避免一次上传整段音频；
3. 使用官方要求的 TLS/证书校验和认证，密钥只从 `secrets/` 读取；
4. LVGL 实现可读性优先的 UI：大号字幕、明显录音键、联网/离线状态、云端错误原因和重试按钮；
5. 将 TTS 解码为 ES8311 可播放的 PCM，播放时处理录音互斥，避免回声与抢占；
6. 加入 Wi-Fi 断线重连、云会话超时、令牌失效、服务器错误与取消操作；
7. 实机做至少 20 次连续短语测试，记录首字延迟、最终文本延迟、TTS 首包延迟、断网恢复和内存峰值。

### 8.3 广角相机到货后

1. 拍摄模组正反面、FPC 触点和包装标签，确认传感器型号、排线针数/方向、CSI lane、电源和 I2C；
2. 对照相机子板原理图，不带电盲插或强行弯折排线；
3. 优先寻找 ESP-IDF/P4 官方或可靠社区中该传感器的驱动；先做单帧抓取、颜色/分辨率/帧率验证，再进 UI 预览；
4. 确认广角畸变、逆光、近距离手势与人脸距离是否符合使用场景；必要时做畸变校正或裁切；
5. 视觉/手语识别模型的部署策略须在相机稳定后另行评估，不承诺直接在 P4 本地跑大型视觉模型。

### 8.4 本轮新建的火山引擎智能体与接入调研

用户已在火山引擎“硬件对话智能体”控制台完成以下配置：

- 创建智能体“聋哑人智能翻译终端”；使用模型为 `doubao-seed-2-0-lite-260428`，配置了“清新女声”；
- 创建产品 `Built_In_V6`，并将上述智能体关联到该产品；
- 产品控制台显示“已激活设备数 0”“已绑定设备 0 台”。这表示云端产品和智能体关系已经建立，但尚无实际硬件设备通过设备端 SDK 成功接入/激活，并非创建失败。

经查证，“SDK 获取”提示所指向的公开代码为 `volcengine/rtc-aigc-embedded-demo`。该工程的架构是：设备端采集/播放音频，RTC 提供低延迟链路，云端处理 ASR、LLM、TTS；这与本项目整体架构一致，可作为协议和链路设计参考。

但必须注意版本和板卡边界：它当前的乐鑫端快速教程只直接支持 **ESP32-S3-Korvo-2 或 AtomS3R**，以 ESP-ADF 特定提交及 ESP-IDF v5.4 为环境。项目现有硬件是 **ESP32-P4X Function EV Board**，已建立 ESP-IDF v5.5.4 + 官方 P4 BSP + ESP-Hosted C6 Wi-Fi 的工程。因此：

1. 不应将该 Demo 当成可直接烧录到 P4X 的现成固件；
2. 不执行其 `git reset --hard`、全局安装 ADF 或修改现有 SDK 的操作；
3. 后续应以它的 RTC/云端会话设计为参考，在当前 P4 工程中编写隔离的适配层；
4. 必须优先确认“硬件对话智能体”产品自身提供的设备 SDK、设备激活方式和鉴权协议，不能假设 ProductKey/Secret 就等价于 P4 的全部运行时凭据。

官方 RTC AIGC Demo 的准备项列出了 AK/SK、RTC AppID/AppKey、流式 ASR AppID/Access Token、TTS AppID/Access Token/Voice Type、方舟 Endpoint ID、硬件场景配置及房间规则。这份清单可用来核对账号能力；但是否需要全部由本项目自行配置，须以“硬件对话智能体”的当前设备端 SDK 文档为最终依据。

## 9. 重要注意事项与风险台账

- **不要泄露凭据**：本文未记录 Wi-Fi 密码、Token 或任何可用密钥。日志也应保持不输出。
- **ProductSecret 已轮换要求**：早前控制台截图曾包含真实 ProductSecret，必须在下次接入前在云控制台生成新值并使旧值失效。本文不保存该值。
- **不要盲目更新 C6**：联网已工作；升级 C6 会改变 P4/C6 的兼容性矩阵。
- **不要删除 `managed_components` 的必要组件**：依赖以 `idf_component.yml` 和 `dependencies.lock` 为准。`managed_components/lvgl__lvgl.stale-cache` 是 Windows 清理失败留下的 Git 忽略缓存，不是源码；需要清理时先精确核对路径。
- **避免多个监控程序同时打开 COM20**：刷写失败时先停止残留 `idf_monitor`，不要反复重插或改驱动。
- **音频实时性与回声**：当前录完再播是正确的硬件验证方式。做全双工云端时要明确半双工交互、回声抑制或按键说话策略，不能直接边录边播。
- **摄像头兼容性不能凭镜头外观判断**：替换模组最大的风险在传感器驱动和 FPC 引脚定义，不是“广角”参数本身。
- **Git 状态**：截至本轮，`.gitignore`、README、docs、firmware、gateway、protocol、tests、tools 等均为未跟踪状态；未来第一次提交前应检查 `git status --short`，确认 `secrets/`、`managed_components/`、构建输出与真实密钥没有被包含。
