## 2. 项目目标与当前实施路线

项目是“聋哑人智能翻译终端”。目标原型的主流程：

```text
板载麦克风 → ES8311 / I2S 采集 → P4 音频任务 → C6 Wi-Fi → 硬件对话智能体
                                                             │
                           7 英寸 MIPI-DSI / GT911 ← LVGL 字幕 ← ASR / 对话结果
                                                             │
外接扬声器 ← ES8311 / I2S 播放 ← P4 音频任务 ← TTS PCM 音频 ←┘

广角 MIPI-CSI 摄像头 → 后续视觉 / 手语模块（新模组尚未到货）
```

软件仍采用 **ESP-IDF + FreeRTOS + 官方 P4 BSP**。P4 不运行通用 Linux“原系统”，不存在应完全重写操作系统以释放性能的必要；ESP-IDF 是板级驱动、MIPI、I2S、SDIO 与 Wi-Fi 协处理器的标准基础。性能关键的音频、图像缓冲可使用已验证的 32 MiB PSRAM。

云端主方案为竞赛方向匹配的火山引擎“硬件对话智能体”。当前采用其官方 `ConversationalAI-Embedded-Kit-2.0` 的高质量 RTC 模式：设备端负责采集、播放、UI 和连接状态，云端负责 ASR、对话编排和 TTS。原先需要独立 Linux/Python 服务端的旧 Demo 不作为本项目主方案。

### 4.5 新增 C6 版本只读诊断

在 P4 获得 IPv4 后，调用官方 ESP-Hosted API：

```c
esp_hosted_get_coprocessor_fwversion(...)
```

该调用是只读 RPC，不会写入、重启或 OTA C6。实机结果：

```text
Host [2.12.0] > Co-proc [0.0.0]
Timeout waiting for Resp for Req_GetCoprocessorFwVersion
hosted: C6 firmware version RPC unavailable (ESP_FAIL)
```

这是今天最关键的诊断证据。说明当前 C6 从端连当前主端所要求的版本查询 RPC 都不支持，现有“P4 主端 / C6 从端”的 ESP-Hosted 协议不匹配是可信主因。它也解释了为什么普通联网能用、而 RTC 这种持续 TLS/高频交互链路表现不稳定。

## 6. C6 升级决策与安全边界

### 6.1 为什么需要直接维护 C6

P4 的 COM20 是 P4 主控的 USB Serial/JTAG 接口，不是 C6 的 ROM 下载端口。C6 与 P4 之间当前走板内 SDIO，正常可以提供 Wi-Fi，但当前从端版本不足以响应版本 RPC。官方的从端 OTA 流程依赖对应的 OTA RPC；既然版本 RPC 已经超时，就不能假定 OTA 具备兼容性或可恢复性。

所以，首次修复 C6 固件应优先采用 **直接 UART 烧录**：通过板上 `PROG_C6` 连接器连到 C6 的 EN、IO0、TXD、RXD、GND。这样即使写入失败，也能用同一下载口恢复。

### 6.2 用户已有 USB-TTL，但当前禁止接线

用户已说明手头有 USB-TTL 下载器；但尚未确认：

- USB-TTL 是 CH340 / CP2102 / FT232 / 其他型号；
- 它是否能选择或固定在 3.3 V **逻辑电平**；
- 引脚丝印实际是 `TXD/RXD/GND/VCC` 还是其他命名；
- 是否有 DTR/RTS，从而支持自动控制 EN/IO0；
- P4X 实物 `PROG_C6` 排针的朝向和每根针旁的丝印。

在照片确认前，**禁止接线**。普通 USB-TTL 与 ESP-Prog 的丝印/信号方向不能机械照搬。

最终接线原则（仅用于之后核对，当前不操作）：

| USB-TTL | P4X `PROG_C6` | 规则 |
|---|---|---|
| GND | GND | 必接，先接地 |
| TXD | RXD | 交叉连接 |
| RXD | TXD | 交叉连接 |
| VCC / 3.3V / 5V | 不接 | P4X 已经由 Type-C 供电；禁止双电源反灌 |
| DTR / RTS | 暂不接 | 只有确认电路和自动下载方式后才决定 |
| EN / IO0 | 由实际下载模式操作决定 | 不可盲接或长期拉低 |

任何 USB-TTL 若只能输出 5 V TTL 电平，不能用于 C6 引脚。仅“供电电压跳帽在 3.3 V”不等于已经确认 TX/RX 逻辑电平，必须看模块型号或实物丝印说明。

### 6.3 下次恢复开发前需要用户提供的材料

1. USB-TTL 正反面高清照片：要拍清型号、跳帽、`TXD/RXD/GND/VCC/DTR/RTS` 丝印；
2. P4X 板上 `PROG_C6` 接口特写：必须看清每个针脚的丝印和排针方向；
3. 若 `PROG_C6` 是空焊盘而没有焊好 2.54 mm 排针，说明是否具备焊接条件；不要先自行焊线；
4. 保持 P4X 通过 Type-C 接电脑、但先不要把 USB-TTL 接到电脑或开发板；
5. 不要按 P4 的 BOOT / RST 键尝试“给 C6 进下载模式”；P4 和 C6 的下载控制不同。

### 6.4 确认材料之后的严格执行顺序

1. 根据照片确认 USB-TTL 电平与精确针脚；
2. 在工作区构建官方匹配的 ESP-Hosted C6 slave（ESP32-C6 + SDIO）；不安装项目专用环境到 C 盘；
3. 检查 `.bin` 镜像、分区表、SHA256 和编译配置；
4. 记录当前 P4 应用和已确认的回退构建产物；
5. 仅接 GND/TX/RX，先用串口验证 C6 输出；
6. 按官方方式隔离 P4 对 C6 reset 的干扰，再将 C6 进入下载模式；
7. 先做 `esptool` 只读芯片识别，成功后才允许写 Flash；
8. 烧录、校验、重启 C6；
9. 重新刷入/启动当前 P4 固件，验证 C6 版本 RPC、Wi-Fi、三个 RTC TCP 探针、动态注册与 `VOLC_EV_CONNECTED`；
10. 只有 RTC 真正连接成功后，才进入 PCM 上下行开发。
