## 1. 今日结论（先读）

1. 昨日语音“开机欢迎语截断、按住说话后没有回复/卡住”的主要根因已经确认：不是 P4 麦克风、扬声器、摄像头或 Wi-Fi 硬件故障，而是旧火山硬件对话设备的单设备基础版可用时长已耗尽。日志表现为机器人入房后约一秒主动离房，因此下行欢迎语和后续会话都会被中断。
2. 用户在火山控制台为产品增加的多个 License 是多个独立设备授权，不会给旧设备叠加可用时长。通过官方动态注册机制更换为新的本地设备名后，P4 自动注册并进入新的设备身份，语音闭环恢复。
3. 当前开发板运行的是已烧录到 COM20 的语音版本：实时 ASR 字幕、松开后的云端回复字幕、云端 PCM 扬声器播放均已从启动和交互日志确认。用户反馈当前“没有大问题”，只剩扬声器偶发轻微卡顿。
4. 已以极小范围修复扬声器轻微卡顿：将播放队列的空闲关停阈值由 500 ms 调整为 1500 ms，避免云端 PCM 帧存在短暂间隙时频繁关闭、重开 I2S。该改动已独立构建、烧录、提交，应用分区仍约有 24% 余量。
5. 用户要求移除屏幕上的“本地录音回放（3秒）”入口。该按钮已从纯文字 UI 删除，固件已构建并烧录；本地回环代码保留为内部诊断能力，但不再有普通用户可触发的屏幕入口。
6. 今日没有重新启用或修改摄像头、SC2336/ISP、SNTP、C6 固件、千帆网关、服务器或 CS001。摄像头开发仍冻结，不能为排查语音而再次混入稳定主线。

## 3. 今日问题定位与处理过程

### 3.1 重新验证本地音频链路

为避免继续对云端或摄像头做无依据修改，先保留并使用了隔离的本地“麦克风录音→扬声器回放”诊断能力。此前用户已实测：本地录音回放声音清晰，仅音量略小。

这提供了关键排除结论：

- ES8311 麦克风采集正常；
- I2S 输入/输出、PCM 缓冲和外接扬声器基础硬件正常；
- 云端无回复不能直接归因于麦克风、扬声器或摄像头；
- 后续云端故障应优先检查 RTC 会话、设备状态和授权，而不是盲目改音频驱动。

对应独立提交：

```text
75c034a test: add isolated local microphone speaker loopback
```

该入口已在今日最后一步从屏幕 UI 移除，详见第 6 节。

### 3.2 诊断火山实时会话中断

COM20 启动/会话日志显示，设备可以完成网络连接、RTC 注册及机器人入房，但机器人会在约一秒后主动离开。该模式可解释用户此前的现象：

- 开机欢迎语只能播出前半句；
- 按住说话后页面停在发送/理解状态；
- ASR 或回复字幕不能完整返回；
- 不是每次都会触发 P4 重启，因此不像典型的内存崩溃或 I2S 初始化失败。

检查火山控制台后确认，旧设备的基础版时长已经超出该设备拥有的授权上限。旧设备的消耗约为 `11.68 / 9` 小时。该平台的 License 是按设备分配的，不是把多个 License 的时长汇总给一个旧设备。

### 3.3 新设备身份与动态注册恢复

为避免手动泄露或硬编码设备密钥，继续使用官方 SDK 的动态注册流程。仅在本机、被 Git 忽略的覆盖文件中指定新的设备名：

```text
secrets\p4x_device_override.h
```

主程序用可选包含方式读取这个本地覆盖；正常工程源码仍不包含设备私密身份。对应提交：

```text
3771d73 feat: support local cloud device identity override
```

新的设备身份在启动后成功完成自动注册并进入 RTC。日志中已经验证：机器人未再即时离房、ASR 字幕返回、松开后获得回复字幕和下行 PCM，扬声器播放任务正常启动。本文不记录完整设备名、房间名、Token 或密钥。

### 3.4 扬声器偶发卡顿缓解

在恢复云端会话后，用户反馈整体已经基本正常，但扬声器偶尔有轻微卡顿。

串口诊断表明，云端 PCM 队列偶有短暂帧间隙。旧逻辑在连续约 500 ms 没有新帧时就关闭 I2S 播放，下一帧到达又重新初始化/开启播放，听感上可能形成很短的断裂。

本次只修改一项播放策略：

| 项目 | 修改前 | 修改后 |
|---|---:|---:|
| PCM 队列空闲后关闭播放的阈值 | 500 ms | 1500 ms |

这样保留短暂的播放等待窗口，不影响回复结束后的正常关闭，也不会增加摄像头、网络或会话模块的资源占用。对应提交：

```text
f5c1a1a fix: tolerate brief cloud audio frame gaps
```

该版本已经单独构建、烧录并保留约 24% 应用分区余量。是否完全消除偶发网络侧 PCM 间隙，仍需要用户在多次真实对话中继续观察；不能将此改动描述为绝对消除所有网络抖动。

## 9. 后续建议顺序（不得跳步）

### 阶段 A：把语音稳定版验收做完

先不改代码，连续进行至少 10 次真实对话：

1. 等待显示云端语音就绪；
2. 按住并说一句完整问题；
3. 松开；
4. 确认按住期间 ASR 字幕出现；
5. 确认只收到一次回复，且字幕和声音都结束；
6. 在一条回复播放中按住新问题，确认可打断；
7. 记录是否有重启、卡住、重复回答、无声音或明显卡顿。

建议固定测试语句：`你好`、`我需要帮助`、`请说一句测试语音`、`我想喝水`、`请用一句话介绍自己`，然后补充 5 次自由提问。

若全部通过，再给该提交打语音稳定标签；若失败，只采集与故障有关的状态日志，先定位后最小修改，禁止顺手重构摄像头/网络模块。

### 阶段 B：单独做网络恢复验收

仅在语音空闲状态下断开并恢复 Wi-Fi，观察设备是否自动回到可说话状态。测试中不烧录 C6、不更换摄像头配置、不引入新的 NTP 策略。

### 阶段 C：以后再开启摄像头独立分支

语音通过验收并建立标签后，才从该标签创建 `feature/sc2336-preview`。摄像头开发必须使用独立配置与独立提交，只做 SC2336 采集/ISP/预览，不接入语音 UI；完成 60 秒预览与 5 次启停无泄漏测试后才讨论手语 MVP。
