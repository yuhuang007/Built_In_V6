## 2. 项目目标与当前架构

项目目标是为聋哑人士制作可交互的智能翻译终端。当前原型路线是：

```text
                 ┌─────────────────────────────────────────────┐
                 │ 火山引擎硬件对话智能体                       │
                 │ ASR → 对话大模型 → TTS / 字幕               │
                 └───────────────┬─────────────────────────────┘
                                 │ C6 Wi-Fi / RTC
┌───────────────────────────┐    │
│ P4X Function EV Board     │────┘
│                           │
│ ES8311 麦克风 → 16 kHz PCM → volc_send_audio_data()
│ 触摸按钮 → 会话状态机 / LVGL 字幕
│ SD 卡 A:fonts/P4ZH14.BIN → 动态中文字形读取
│ 云端字幕 → cJSON → 屏幕“你 / 助手”文本
│ 云端 TTS → 暂不写入扬声器（待格式确认）
└───────────────────────────┘

后续广角 MIPI-CSI 摄像头到货后，再加入手语/视觉功能；本轮未涉及摄像头驱动或模型。

软件基础继续使用 **ESP-IDF + FreeRTOS + 乐鑫 P4 BSP + LVGL**。P4 不是运行普通 Linux 的“原系统”，不需要也不建议脱离 ESP-IDF 重写操作系统；性能隔离应使用任务优先级、DMA、PSRAM、双缓冲和必要时的云/边协同。

## 4. 本轮代码修改

主修改文件：

`firmware\p4_main\main\main.c`

### 4.1 中文省略号兼容修复

完整 SD 字库覆盖范围为：

```text
0x20-0x7F
0x3000-0x303F
0xFF00-0xFFEF
0x4E00-0x9FFF
```

未覆盖 `U+2026`。已把所有硬编码的 `……` 替换成 `...`，涉及云连接、同步、发送、聆听、理解、回复和字库同步状态文案。该方案避免重新生成和传输字体文件，且保证屏幕不会再因省略号显示方框。

### 4.2 修复语音结束提交逻辑

旧逻辑在第二次点击时立刻将 `conversation_recording=false`，导致采集循环退出，永远没有机会发送 `commit=true` 的最后一帧。

现采用两个状态量：

```c
static volatile bool conversation_recording;
static volatile bool conversation_finish_requested;
```

流程改为：

1. 首次点击：`conversation_recording=true`，`conversation_finish_requested=false`，开启采集任务；
2. 第二次点击：只设置 `conversation_finish_requested=true`；
3. 采集任务再读取一个真实 PCM 帧，以 `info.commit=true` 上传；
4. 输出累计帧数、字节数、上传失败数，再关闭麦克风和复位状态。

这是本轮最重要的设备端修复，实机日志已证明最终提交帧确已送出。

### 4.3 增加不泄露凭据的诊断日志

新增或强化：

- 音频上传失败时输出帧序号、是否 commit、错误码；
- 最终提交时输出帧数、字节数和失败数；
- `volc_interrupt()` 失败时输出错误码；
- 消息回调输出数据长度、是否字幕帧、JSON `type`，但不打印 Token、密钥、房间配置；
- 字幕 JSON 解析失败输出长度，不打印潜在敏感缓冲内容。

### 4.4 与火山官方 RTC 高质量示例对齐 `params`

参考用户本机下载的 Kit：

`E:\zhoumian\Built-In\ConversationalAI-Embedded-Kit-2.0-main_Korvo_2\examples\high_quality_solution\espressif\main\conv_ai_embedded_kit.c`

已在 `VOLC_RTC_CONFIG_FORMAT` 的 `rtc.params` 中添加官方示例使用的：

```json
{"debug":{"log_to_console":1}}
{"audio":{"codec":{"internal":{"enable":1}}}}
{"rtc":{"access":{"concurrent_requests":1}}}
{"rtc":{"ice":{"concurrent_agents":1}}}
```

其中第 2～4 项关系到 RTC 内部音频能力和并发 Agent/ICE 接入。保留 `rtc.log_level=4`，避免供应商预编译库在 INFO 级别泄露一次性会话 Token。此改动已构建并成功烧录，但其效果尚待自动文字自检结果确认。

### 4.5 新增一次性云端纯文本自检（当前测试固件）

每次设备启动并收到 `VOLC_EV_CONNECTED` 后，延迟约 1.5 秒执行一次：

```c
volc_send_text_to_agent(cloud_engine, request, VOLC_AGENT_TYPE_LLM);
```

固定请求只询问“文字链路正常”，用于验证：

```text
P4 → RTC → 智能体 LLM 命令 → 字幕/响应回传 → LVGL
```

它不依赖真人讲话，也不依赖扬声器播放。它是**临时调试代码**：确认链路后，应删除或改为隐藏的“诊断模式”开关，绝不能在最终产品的每次启动自动向云端发送请求。

## 6. 当前未解决问题与判断边界

### 6.1 用户可见现象

屏幕在第二次点击后稳定显示：

```text
语音已发送，正在理解你说的话...
你：正在聆听...
助手：--
```

这与“设备上行音频提交成功、云端业务没有产生可见回调”一致。

### 6.2 已排除或暂不优先的方向

- 不是中文字体主体缺失：大量固定中文均正常；
- 不是触摸按钮没有触发：有坐标和点击日志；
- 不是麦克风未打开：I2S 与 ES8311 打开日志存在；
- 不是最后提交帧漏发：已看到 `commit` 成功的统计；
- 不是本轮 C6 被误刷坏：本轮没有写入 C6；
- 不是扬声器本身导致：文字状态/字幕也完全没有回调，且下行播放当前故意禁用。

### 6.3 仍待区分的根因

1. 火山控制台上的智能体是否已“发布/启用”，是否真正绑定到当前产品和激活设备；
2. RTC 房间里是否存在机器人用户但未订阅/消费设备的上行音频轨道；
3. 当前 RTC `audio.codec=3` 与 SDK `VOLC_AUDIO_DATA_TYPE_PCM`、16 kHz / 16-bit / mono 的实际协商是否匹配；
4. `rtc.params` 补齐后，纯文本 `ExternalTextToLLM` 命令是否能被智能体接收；
5. SDK 是否将某些控制/错误信息以 `conv`、`tool` 等消息帧返回，而应用当前只重点解析 `subv`；后续必须记录消息魔数和安全的长度/类型信息，但不能直接把二进制或敏感 JSON 全量打到串口。

## 7. 下一步严格执行顺序

### 第一步：获得自动文字自检结果（优先，不需要讲话）

1. 上电并等待网络与 RTC 就绪；
2. 观察屏幕是否依次出现“正在进行云端文字自检...”和“文字请求已发送，等待智能体回复”；
3. 等待 10～15 秒；
4. 拍下屏幕；
5. 读取 `logs\p4_text_selftest.log`。

结果解释：

| 结果 | 结论 / 后续 |
|---|---|
| 显示“文字链路正常”或助手字幕 | 智能体与回传可用；下一步集中检查 RTC 音频轨道参数、采样率与发布订阅 |
| 纯文本 API 返回失败 | 查 SDK 错误码、RTC 状态、智能体的可用性/权限 |
| API 返回成功但无回复 | 高概率控制台智能体未发布、未启用、绑定错误，或云端没有处理该设备会话；进入控制台核对 |
| 未到 RTC connected / 自检根本没触发 | 先抓完整启动日志，检查 Wi-Fi、SNTP、动态注册、RTC join |

### 第二步：控制台核对（若文字自检无回复）

在火山引擎硬件对话智能体控制台，用户需确认并截图非敏感页面：

- 当前智能体状态是否为已发布/启用，而非草稿；
- 智能体是否绑定到产品 `Built_In_V6`；
- 当前设备是否激活/在线、是否为同一个 DeviceName；
- 是否启用了 ASR、LLM、TTS 以及字幕能力；
- 控制台是否存在设备会话、错误日志或调用配额/权限告警。

不要截图或发送 ProductSecret、Token、AppKey、房间名等机密字段。

### 第三步：若文字自检通过，再查音频协议

1. 在 `cloud_audio_callback()` 内只记录 `info` 的非敏感格式字段和数据长度，仍不播放；
2. 消息回调覆盖 `subv`、`conv`、`tool` 的帧类型，做长度边界检查；
3. 确认 SDK 的上行 PCM 格式要求；
4. 必要时改用官方高质量示例相同的录音数据块大小/节奏；
5. 只有已确认“PCM、采样率、声道、位深”后，才将下行数据送入 ES8311，先低音量短句验证，避免恢复杂音。

### 第四步：收尾调试代码

验证完成后：

- 删除/关闭自动文字自检；
- 保留可控、脱敏的诊断日志；
- 设计超时 UI（例如 15 秒无回调时提示“云端未回复，可重试”），而不是永久卡在“正在理解”；
- 设计断线重连、单会话互斥、连续点击防抖、回声抑制和音频队列；
- 再进入摄像头与手语功能开发。
