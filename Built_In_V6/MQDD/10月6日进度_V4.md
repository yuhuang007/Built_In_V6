## 3. 今日对话与开发过程

### 3.1 开始今日开发：语音链路仍无回复

今日开始时 COM20 在线。用户反馈：

- 开机能听到“你好，请点击屏幕开始说话”；
- 用户说“你好，请告诉我今天是星期几”后无反馈；
- 本地录音回放清晰正常，只是音量稍小；
- 多次提交语音后仍没有云端回复。

这说明麦克风、I2S 和本地 PCM 基础链路可用，问题需要从 RTC/智能体业务链路和会话状态继续查，而不是把故障简单归因于麦克风硬件。

随后通过火山控制台检查设备/智能体状态。期间出现过：

- 扬声器刚发出“你好”设备就重启；
- 设备进入反复重启；
- 调整后设备恢复正常启动；
- 屏幕出现云端状态，但扬声器没有声音；
- 等待超过一分钟仍卡在当前界面；
- 有文字反馈但没有声音；
- 必须再按“结束”才开始播放声音，而回复文字已经提前显示。

这些现象推动了后续对音频队列、回复首帧和会话结束状态的整理。

### 3.2 语音交互改为“按住说话、松开结束”

用户明确要求按钮逻辑改为：

```text
按下并保持：开始录音
松开：提交尾帧并结束录音
云端返回首个可播放 PCM：同步显示助手字幕并开始播报
```

语音交互目标随后固定为：

- 按住期间显示用户 ASR 字幕；
- 松开后只生成一次回复；
- 回复文字不能明显早于声音开始；
- 上一条回复正在播放时，用户再次按住应当允许打断并开始新问题；
- 录音状态松开即可结束，不应要求再点击一次；
- 不得长期卡在“当前对话尚未结束”或“正在理解上一句话”。

期间曾出现两个状态机回归：

1. 一次对话结束后，再次按下始终提示“当前对话尚未结束，请稍后”；
2. 修改打断逻辑后，又长期提示“正在理解上一句话”。

随后恢复“回复中允许打断”的优先行为，并调整空闲、录音、尾帧、思考、回答、恢复状态之间的切换。用户阶段性反馈“目前来看没问题了”，说明在摄像头开发开始前，语音链路曾达到可用状态。

用户询问“今天是星期几”时，智能体出现先回答具体星期、随后又回答“无法获取实时日期信息”的重复/冲突回复。讨论过：

但这条路线增加了服务器、网关、第二套模型和网络依赖，偏离单板原型设计。用户要求重新阅读原项目说明，最终决定：

- 删除 ASR 文本重复提交 LLM 的绕行逻辑；

这次纠偏非常重要：日期、天气和搜索不是当前比赛原型的核心验收项，不能继续消耗 P4 的资源和调试时间。

- `E:\系统软件\下载\1.0K-GT-15PB_specification.pdf`

从摄像头子板 PCB 丝印可确认路线为 `MIPI_Sub For SC2336`。当前硬件判断：

| 项目 | 结论 |
|---|---|
| 传感器 | SC2336 路线 |
| 连接 | MIPI-CSI 排线，不是 USB/HDMI |
| 原始输出 | RAW（资料存在 RAW8/RAW10 表述，实际应以当前驱动枚举为准） |
| 预览需求 | 需要 P4 ISP 将 RAW 转换为 LVGL 可显示的 RGB565 或其他显示格式 |
| 屏幕 | 1024×600 MIPI-DSI，EK79007 控制器路线 |
| 触摸 | GT911 |

关键错误是把 RAW 传感器节点直接当作可输出 RGB565 的显示节点。实时预览所需的正确逻辑应是：

```text
SC2336 RAW
    → MIPI CSI
    → ESP32-P4 ISP
    → RGB565（低分辨率）
    → 独立 PSRAM 显示缓冲
    → LVGL 图像对象
```

但当前 ESP-Video/ISP 节点的实际设备枚举、驱动格式协商和 pipeline controller 配置没有完全跑通，导致：

- “摄像头格式读取失败”；
- “摄像头启动失败：ESP_FAIL”；
- 实时画面无法显示。

### 3.9 SNTP 逻辑回滚

曾尝试的多服务器/多轮重试逻辑包含：

- 多个国内 NTP 服务器；
- 三轮 `esp_sntp_stop()` / `esp_sntp_init()`；
- 自动延迟重注册；
- 更多 UI 重试状态。

该修改与摄像头变更叠加后增加了不确定性。用户贴出的代码对比看起来像重复拼接，但实际是变更对比：一侧是被删除的新重试逻辑，另一侧是恢复的旧逻辑，并非当前源文件中同时存在两套代码。

当前已恢复为此前较稳定的简单流程：

```c
esp_sntp_setoperatingmode(SNTP_OPMODE_POLL);
esp_sntp_setservername(0, "cn.pool.ntp.org");
esp_sntp_setservername(1, "ntp1.aliyun.com");
esp_sntp_init();

for (int retry = 0; retry < 15; ++retry) {
    time(&now);
    localtime_r(&now, &time_info);
    if (time_info.tm_year >= (2025 - 1900)) {
        return true;
    }
    vTaskDelay(pdMS_TO_TICKS(1000));
}
return false;
```

当前配置中 `CONFIG_LWIP_SNTP_MAX_SERVERS=1`。注意：代码仍设置了两个服务器名，而配置最大服务器数为 1；后续若继续整理网络代码，应核对 SDK 对第二个索引的行为，但在语音验收前不再改动。

### 3.10 摄像头实验隔离时出现一次编译错误

## 8. 根因与教训

### 8.1 为什么原本好的语音被改坏

不是单一语句错误，而是开发流程失控：

1. 在没有有效 Git 基线的情况下继续修改；
2. 同一轮同时调整音频状态机、网络恢复、SNTP、ESP-Video、ISP、LVGL 和内存资源；
3. 摄像头实验直接混入稳定语音固件；
4. 构建成功后没有先完成语音回归测试，就继续叠加功能；
5. 对“设备未找到”的 UI 提示缺少硬件节点和格式证据；
6. 没有在每个已验收阶段立即提交并打标签。

### 8.2 后续强制开发规则

后续任何开发者或 AI 必须遵守：

1. 开始前执行 `git status --short --branch`；
2. 稳定状态先提交，工作区必须干净；
3. `master` 只保存已实机验收的语音主线；
4. 摄像头使用 `feature/sc2336-preview` 独立分支；
5. 摄像头使用独立 `sdkconfig.camera` 或等效配置，不修改稳定 `sdkconfig.display`；
6. 一次只改变一个子系统；
7. 每次烧录前记录 commit ID、固件大小和配置；
8. 每次烧录后先跑完整回归，再继续下一项；
9. 不得用 `git reset --hard` 或覆盖用户文件；
10. 不得把密钥、Wi-Fi 密码或 Token 提交到仓库；
11. 未经用户实测，不得写“已完成”；
12. 摄像头失败不得修改 C6 固件，语音失败不得随意修改摄像头驱动。
