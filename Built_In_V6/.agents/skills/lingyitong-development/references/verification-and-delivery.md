# 验证、参赛和收尾

## 证据各自证明什么

| 证据 | 可以说明 | 不能代替 |
|---|---|---|
| 文件/哈希 | 版本绑定与传输完整 | 算法和功能正确 |
| 静态/宿主测试 | 对应逻辑和受测边界 | 完整LVGL、硬件或真实识别 |
| 保存预测复算 | 指标和标签对账 | 重载权重或新输入推理 |
| 冻结权重/缓存推理 | 对应输入推理可复现 | 摄像头前端和跨人泛化 |
| 构建/烧录 | 镜像生成和写入成功 | 实机功能通过 |
| 用户定性反馈 | 对应版本真实体验 | 无记录的准确率和长期指标 |
| 短时无异常 | 该窗口观察结果 | 根因修复、长期稳定或未操作功能 |

按证据类型填写状态，不用一个“完成”覆盖所有层级。给实机检查时列有限操作、预期结果和需要观察的现象，复用已有反馈，不让用户重复验证无变化项目。

## 参赛规划

读取原始赛题，维护“条款/出处→对应能力→现状→缺口→验收→展示证据”。区分赛题硬要求、用户目标、旧建议指标。硬要求口径不清先定位具体疑点，避免自己宣布满足或盲目加硬件。

优先级依据用户当前选择、必备条款、完整演示链路、阻塞及成本制定；不因研究新颖就扩大到不匹配算力的完整预训练。文档/PPT准确表述复用、创新和未完成项，不将电脑能力包装为P4离线部署。

## 交付与文档更新

开发最终回复聚焦：实际行为变化、测试及实机覆盖、版本/入口、未关闭问题。无需每次列全历史或输出大报告。

确需更新MQDD时，在对应记录追加本次事件或创建一份本轮记录，注明：
- 本轮目标、范围和实际操作。
- 源码/构建/板上固件或模型版本，以及证据来源/实际运行者。
- 验证结果、用户反馈和未验证范围。
- 被新结果替代的旧状态；下一步为建议还是已安排任务。

纯分析不强制落盘，纯文档不构建/烧录。不要每轮复制全部旧交接；只更新必要入口和变化。用户停工后不自动继续训练、服务、轮询或提醒。
